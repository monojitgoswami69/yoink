Chapter 01 · Getting started

Quickstart

Four commands take you from nothing to a healthy stack.

yoink setup                                # provider, model, API key (optional)
yoink init https://github.com/owner/repo   # clone → generate → build & heal
yoink up myrepo                            # start, waits for healthchecks
yoink dash myrepo                          # live dashboard

A project is a locally-managed instance of an initialized repository. The project name is the repo name unless you pass --name; it is the identifier every later command uses. Omitting it targets the most recently initialized project.

Useful init flags

FlagEffect
--nameOverride the project name (defaults to the repo name)
--no-agentPure static analysis: no API key, no LLM round-trips
--forceRe-initialize over an existing project
--output <dir>Write generated files somewhere other than the default
--no-buildSkip the build/heal stage (works without Docker)
--heal-tries NCap heal attempts (default 3)
--max-services NCap how many services detection may emit

Accepted URL forms

https://github.com/<owner>/<repo> https://github.com/<owner>/<repo>.git https://github.com/<owner>/<repo>/tree/<branch>[/<subdir>] git@github.com:<owner>/<repo>[.git]
Chapter 02 · Installation

Installation

Yoink ships as a single binary you build once. Docker is only needed at run time.

curl -fsSL https://raw.githubusercontent.com/monojitgoswami69/yoink/main/install.sh | bash

Clones the repo, builds with Go (-ldflags "-s -w"), and installs to ~/.local/bin. Set YOINK_INSTALL_DIR to choose another location. If that directory is not on your PATH, add it:

export PATH="$HOME/.local/bin:$PATH"

Then verify:

yoink --version
git clone https://github.com/monojitgoswami69/yoink.git
cd yoink
go build -o yoink .
sudo mv yoink /usr/local/bin/

Or use the Makefile, which stamps version info at build time: make build install (installs to /usr/local/bin, override with PREFIX).

git clone https://github.com/monojitgoswami69/yoink.git
cd yoink
go build -o yoink.exe .

Add the directory to your PATH, or move yoink.exe somewhere already on it. Docker Desktop provides the runtime.

Requirements

Build time Go 1.21+

Only to compile the binary.

Build time git

Used for cloning target repositories.

Run time Docker Engine + Compose v2

Your existing installation. Skip with --no-build.

Chapter 03 · Reference

How detection works

yoink init walks the cloned tree, ignoring node_modules/, .venv/, .git/, dist/, build/, and monorepo noise such as examples/, tests/, and docs/. Each deployable unit becomes a Service record:

FieldMeaning
IDStable id (service-1, …) used as the Compose service name
DirectoryPath relative to repo root (empty means root)
Languagejavascript, typescript, or python
Frameworknext, express, fastapi, …
PackageManagernpm / yarn / pnpm / pip / poetry, picked from lockfiles
InstallCmd BuildCmd StartCmdConcrete commands the generated Dockerfile runs
PortContainer port exposed and published; refined by regex over entry files such as .listen(4000)
Confidencehigh / medium / low; low-confidence extras are dropped first at --max-services

Workspace-root package.json files, and libraries with no framework and no start script, are skipped automatically. With an LLM configured (and without --no-agent), the detection result and repo tree are also validated by the model, which may request up to 5 files per round through the sandboxed reader.

Infrastructure inference

After env-var extraction, references are scanned for hints. Each match adds a Compose service with sensible defaults, a healthcheck, a named volume where stateful, and a depends_on: service_healthy edge from every app service that references it.

Chapter 05 · Guide

The build/heal loop

After generation, yoink init runs docker compose build against your daemon (unless --no-build or Docker is absent). On failure:

  1. Compose output is captured and the failing service extracted.
  2. The Dockerfile, Compose file, and last 80 lines of error go to your configured LLM with a fix prompt.
  3. The model returns a corrected Dockerfile, a corrected compose file, or a request for more files (served through the sandboxed reader).
  4. The fix is written back to the same files under yoink-outputs/ and the build retries.
  5. Attempts stop at --heal-tries (default 3). Non-convergence ends in a readable summary of what failed each round.

You can re-run the loop against an existing project any time:

yoink heal myrepo            # re-attempt the build/heal loop
yoink heal --tries 5 myrepo  # more attempts

Every applied repair is recorded in project state, so yoink explain myrepo can list what the agent changed without invoking the LLM again.

Chapter 06 · Reference

State & generated outputs

Each initialized repo gets a persistent state directory, so later commands never need re-detection or repeated input:

~/.yoink/state/<repo>/ ├── yoink.lock # metadata, services, port map, detection hash ├── env-overrides.json # your edited values, applied at yoink up └── settings.json # preferences

The detection hash inside yoink.lock lets re-runs notice when the upstream repo changed in ways that invalidate the generated stack.

What lands in your repo

yoink-outputs/ ├── docker-compose.yml # app services + inferred infra ├── Dockerfile.service-1 # one per service ├── Dockerfile.service-2 ├── env-vars/ │ └── <service>/ │ ├── .env.example # template, safe to commit │ └── .env # real file compose reads, gitignored ├── quick_start.md └── .gitignore # keeps .env out, lets .env.example through
  • Compose build context is the repo root; each Dockerfile copies from its sub-directory, so monorepos work without tricks.
  • env_file: points at .env, which yoink up rebuilds from .env.example plus overrides before starting.
  • Host port collisions are remapped automatically by probing the host for free ports.
  • All Dockerfiles install curl so compose-level healthchecks work out of the box.

Dashboard guide

yoink dash [project] opens a multi-pane Bubble Tea TUI. Top: service list with status, health, and bound URLs. Middle: tabbed pane. Bottom: live docker stats strip.

KeyAction
↑ ↓Select service
tabNext pane (Logs, Env, Controls)
s / xStart / stop selected service
r / bRestart / rebuild selected service
eEdit env in $EDITOR; saves to env-overrides.json and recreates just that service
pgup/pgdown, g/GScroll log tail; jump to top / bottom

Env edits made in the dashboard persist across runs and apply on the next yoink up.

Chapter 08 · Guide

Environment handling

App configuration lives in two layers: the generated per-service .env.example templates, and your overrides.

yoink env myrepo list         # show current values (secrets masked)
yoink env myrepo set KEY=val  # write an override
yoink env myrepo unset KEY    # remove an override
  • Secret-looking names containing SECRET, PASSWORD, TOKEN, CREDENTIAL, PRIVATE_KEY, or API_KEY are always masked in output.
  • Overrides are stored per project in env-overrides.json, never written into the repo's templates.
  • yoink up merges template + overrides into the runtime .env before invoking Compose.
  • yoink explain myrepo lists any variables still required (empty values or placeholders), separated into secrets vs plain configuration.

Chapter 10 · Guide

Configuration & LLM providers

yoink setup is an interactive wizard that writes ~/.yoink/config.json with 0600 permissions:

{
  "llm_provider": "openai",
  "llm_model": "gpt-4o",
  "llm_api_key": "...",
  "github_pat": "ghp_..."
}

Supported providers

ProviderNotes
openaiDefault cloud option (Chat Completions)
anthropicMessages API; strong reasoning for the heal loop
groqOpenAI-compatible; fast, low-latency inference
geminiGoogle GenerateContent API; cost-efficient cloud option
ollamaFully local via localhost:11434; the API key step is skipped

The GitHub PAT step is optional. When set, clones inject an Authorization header through git -c http.extraheader=…, so the token never appears on the command line or in .git/config, and the header config is removed from the clone after success.

Per-project knobs (heal tries, auto-heal, provider overrides) live under yoink config <project>.

Chapter 11 · Reference

Security model

Yoink gives an LLM limited, sandboxed access to your code and keeps hard limits everywhere else.

Sandboxed file access

The model reads only repo-relative paths inside the cloned root. Absolute paths, .. traversal, and symlinks pointing outward are rejected. Reads are capped at 16 KiB per file, at most 5 files per round.

Secrets stay local

GitHub PATs travel through git's http.extraheader, never argv or .git/config, and are stripped after clone. Config is stored with 0600 permissions; secret input is masked.

Bounded autonomy

The heal loop stops after --heal-tries attempts, default 3, and reports exactly what changed per attempt. No runaway retries, ever.

Offline when you want it

Ollama keeps everything local, and --no-agent disables the LLM entirely: deterministic static analysis, no key, no network calls.

Chapter 12 · Answers

Frequently asked questions

Do I need an API key to use Yoink?+
No. Run yoink init --no-agent for pure static detection and generation, or configure Ollama in yoink setup to use a local model with no key. An API key only unlocks the LLM validation passes and the build/heal loop.
Which languages and frameworks are supported?+
JavaScript/TypeScript: Next.js, NestJS, Fastify, Express, Koa, Hapi, Vite, Create-React-App, plain React, and generic Node. Python: FastAPI, Django, Flask, and generic Python. Go, Rust, and Java are not detected today.
Does it work with private repositories?+
Yes. Add a GitHub PAT in yoink setup. It's injected through git's http.extraheader, never the command line or .git/config, and removed from the clone after success.
Do I need Docker installed?+
Only to build and run stacks. Yoink uses your existing Docker Engine and Compose v2; it installs no daemon. Generation alone works without Docker via yoink init --no-build.
What happens if the heal loop can't fix a build?+
Attempts are capped, default 3, tunable with --heal-tries. On non-convergence you get a readable summary: which service failed, what was tried, and what changed each round. You can re-run later with yoink heal.
What gets sent to the LLM?+
The detection summary, repository tree, the failing Dockerfile or Compose file, and the last 80 lines of build output. The model may request up to 5 additional files per round, 16 KiB each, read through a sandbox that rejects anything outside the cloned repo.
Where does Yoink keep its state?+
Per project, under ~/.yoink/state/<repo>/: a detection lock, your env overrides, and preferences. yoink remove deletes a project's state; volumes are kept unless you pass --volumes.
Is this a deployment tool?+
No. Yoink runs stacks on your local Docker only; multi-host orchestration and Kubernetes are explicitly out of scope. It's built for the clone-to-running loop on your machine.
