01 · The problem

The barrier isn't a missing Dockerfile.
It's the whole chain.

Cloning an unfamiliar repo today means writing or fixing Docker configs, orchestrating services, hunting env vars, and debugging builds by hand. Tools like docker init and buildpacks generate files, then walk away.

No Dockerfile, or an outdated one

Writing one means knowing the framework's build conventions.

→

Yoink writes one framework-level Dockerfile per service. A Next.js app and a Flask API get genuinely different recipes.

Multi-service orchestration

Monorepos need a Compose file that wires frontends, backends, and workers together.

→

Yoink is monorepo aware: deployables in apps/* and services/* become one Compose project.

Undeclared infrastructure

Code references PostgreSQL or Redis that Compose never provisions. Silent runtime failures follow.

→

Yoink sees DATABASE_URL in your source and adds Postgres with a healthcheck and a wired connection string.

Scattered environment variables

Config lives across dozens of files with no consolidated template.

→

Every process.env, os.getenv, VITE_, and NEXT_PUBLIC_ reference lands in a per-service .env.example.

Build failures demand Docker fluency

One bad layer and a newcomer is stuck reading compiler spew.

→

Failing builds go to the LLM heal loop, which applies a fix and retries, capped at three attempts.

Tools generate files and walk away

Scaffolding isn't a running application.

→

Yoink builds, verifies against your Docker daemon, and hands off a healthy stack with a live dashboard.

02 · How it works

Eight steps. One command.

Every yoink init runs the same auditable pipeline: deterministic first, LLM second, verification always.

  1. 01

    Clone

    HTTPS, SSH, branch, or sub-directory URLs. PATs travel through git's header, never the command line.

  2. 02

    Map the tree

    Walks the repo, skipping node_modules, .venv, build output, and monorepo noise.

  3. 03

    Detect services

    14 framework profiles across Node and Python, each with a confidence rating.

  4. 04

    Extract env vars

    Source-level references become a per-service .env.example template.

  5. 05

    Infer infrastructure

    Env hints and dependency lists add backing services with healthchecks and volumes.

  6. 06

    Generate

    One Dockerfile per service plus a single docker-compose.yml with port-collision avoidance.

  7. 07

    Write outputs

    Everything lands in yoink-outputs/ with a .gitignore that keeps real secrets out.

  8. 08

    Build & heal

    Builds against your Docker daemon. On failure, the LLM patches the config and retries, up to 3 times.

03 · Features

Generate, run, heal.
Then drive it daily.

Most generators stop at files. Yoink stays for the build, the failure, the fix, and every restart after that.

Self-healing builds

When a build fails, Yoink captures the failing service and the last 80 lines of output, sends them along with the Dockerfile and Compose to your configured LLM, applies the returned fix, and retries. Bounded by --heal-tries, default 3. If it can't converge you get a readable failure summary, not an infinite loop. Re-run any time with yoink heal.

✗ service "api" failed to build → sent Dockerfile + compose + last 80 lines to the LLM → patch applied (attempt 1/3) ✓ Build succeeded

Infrastructure inference

Env-var references and dependency manifests are scanned for infrastructure hints. Each match adds a Compose service with a healthcheck, a named volume, and a depends_on: service_healthy edge.

DATABASE_URL → postgres:16-alpine REDIS_URL → redis:7-alpine MONGO_URI → mongo:7 + MySQL · RabbitMQ · Elasticsearch

Framework-aware generation

Multi-stage builds for Next.js and NestJS, nginx for static SPAs, slim images for Python. Package managers such as npm, yarn, pnpm, pip, and poetry are picked from lockfiles, and ports are read from entry files.

nextnestfastifyexpressvitefastapidjangoflask+6 more

Monorepo-native

Compose build context sits at the repo root, so each Dockerfile copies from its own sub-directory. Workspace-root package.json files and libraries without start scripts are skipped automatically.

COPY apps/web/package*.json ./ RUN npm ci && npm run build

It remembers you

Env values, port choices, and detection state persist per repo. Your second yoink up needs zero input.

~/.yoink/state/fastapi-template/ ├── yoink.lock ├── env-overrides.json └── settings.json

Any LLM, or none at all

Pick a provider once in yoink setup; the choice persists. Prefer zero cloud calls? Run Ollama locally for a fully offline mode, or pass --no-agent for pure static analysis with no API key and no LLM round-trips.

OpenAI Anthropic Groq Google Gemini Ollama · local --no-agent · static only

05 · Install

Up and running
in under a minute.

Yoink ships as a single binary you build once. Docker is only needed when you run stacks; init --no-build works without it.

curl -fsSL https://raw.githubusercontent.com/monojitgoswami69/yoink/main/install.sh | bash

Clones the repo, builds with Go, and installs to ~/.local/bin. Set YOINK_INSTALL_DIR to choose a different location. Then verify:

yoink --version
git clone https://github.com/monojitgoswami69/yoink.git
cd yoink
go build -o yoink .
sudo mv yoink /usr/local/bin/

Or use the Makefile, which stamps version info at build time: make build install.

git clone https://github.com/monojitgoswami69/yoink.git
cd yoink
go build -o yoink.exe .

Add the directory to your PATH, or move yoink.exe somewhere already on it. Docker Desktop provides the runtime.

What you need

Build time Go 1.21+

Only to compile the binary. Nothing else.

Build time git

Used for cloning target repositories.

Run time Docker Engine + Compose v2

Your existing installation. Yoink adds no daemon or shim. Skip it with --no-build.

Then your first stack

yoink setup                                # provider, model, API key (optional)
yoink init https://github.com/owner/repo   # clone → generate → build & heal
yoink up myrepo                            # start, waits for healthchecks
yoink dash myrepo                          # live dashboard

Useful init flags: --name, --no-agent, --force, --output, --no-build, --heal-tries N, --max-services N. Accepted URLs include HTTPS, .git, SSH, and /tree/<branch>/<subdir> forms.

07 · Trust & control

Powerful by default.
Bounded on purpose.

Yoink gives an LLM limited, sandboxed access to your code and keeps hard limits everywhere else.

Sandboxed file access

The model reads only repo-relative paths inside the cloned root. Absolute paths, .. traversal, and symlinks pointing outward are rejected. Reads are capped at 16 KiB per file, at most 5 files per round.

Secrets stay local

GitHub PATs are injected through git's http.extraheader, never the command line or .git/config, and stripped after clone. Config lives at ~/.yoink/config.json with 0600 permissions; input is masked.

Bounded autonomy

The heal loop is capped at --heal-tries attempts, default 3. Non-convergence ends in a human-readable summary of what failed and what was attempted, never a runaway retry loop.

Offline when you want it

Choose Ollama for a fully local model, or --no-agent for pure static analysis: no API key, no network calls to any LLM, deterministic output.

Providers: OpenAI (default cloud) · Anthropic (strong reasoning) · Groq (low latency) · Google Gemini (cost-efficient) · Ollama (local, no key). Selected once in yoink setup, persisted in config.

09 · FAQ

Sensible questions,
straight answers.

Do I need an API key to use Yoink?+
No. Run yoink init --no-agent for pure static detection and generation, or configure Ollama in yoink setup to use a local model with no key. An API key only unlocks the LLM validation passes and the build/heal loop.
Which languages and frameworks are supported?+
JavaScript/TypeScript: Next.js, NestJS, Fastify, Express, Koa, Hapi, Vite, Create-React-App, plain React, and generic Node. Python: FastAPI, Django, Flask, and generic Python. Go, Rust, and Java are not detected today.
Does it work with private repositories?+
Yes. Add a GitHub PAT in yoink setup. It's injected through git's http.extraheader, never the command line or .git/config, and removed from the clone after success.
Do I need Docker installed?+
Only to build and run stacks. Yoink uses your existing Docker Engine and Compose v2; it installs no daemon. Generation alone works without Docker via yoink init --no-build.
What happens if the heal loop can't fix a build?+
Attempts are capped, default 3, tunable with --heal-tries. On non-convergence you get a readable summary: which service failed, what was tried, and what changed each round. You can re-run later with yoink heal.
What gets sent to the LLM?+
The detection summary, repository tree, the failing Dockerfile or Compose file, and the last 80 lines of build output. The model may request up to 5 additional files per round, 16 KiB each, read through a sandbox that rejects anything outside the cloned repo.
Where does Yoink keep its state?+
Per project, under ~/.yoink/state/<repo>/: a detection lock, your env overrides, and preferences. yoink remove deletes a project's state; volumes are kept unless you pass --volumes.
Is this a deployment tool?+
No. Yoink runs stacks on your local Docker only; multi-host orchestration and Kubernetes are explicitly out of scope. It's built for the clone-to-running loop on your machine.
